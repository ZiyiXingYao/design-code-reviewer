# design-code-reviewer

> 让"评审"从一次性对话变成可复现、可审计的流程：固定判据、批级落盘、红蓝裁对抗、出报告前强制闸门。

两个 CodeBuddy 技能，用来评审「先出设计文档、再出实现」的项目：

| 技能 | 标识符 | 审什么 | 不做什么 |
|---|---|---|---|
| 设计评审 | `design-review` | 设计方案是否合理、功能是否完整、产物是否合规 | 不读代码、不改文档 |
| 实现评审 | `impl-review` | 代码是否兑现了设计 + 通用正确性/安全 | 不评架构合理性、不改代码 |

两者**完全独立、互不调用**。唯一交接物是设计评审报告末尾的「交接块」（设计基线、欠账白名单、设计约束 `C-n`）。

## 安装

```bash
node install.mjs --dry-run     # 看会装到哪
node install.mjs               # 安装到 ~/.codebuddy/skills/{design-review,impl-review}
node install.mjs --uninstall   # 卸载
```

零依赖，需要 Node ≥ 20。

## 触发

- 设计评审：「评审设计方案」「这个架构合理吗」「模块划分有没有问题」「这份设计能不能开工」
- 实现评审：「评审代码」「实现符合设计吗」「合并前检查」「这个 MR 有没有问题」

## 它解决什么

评审最常见的三种失败：

| 失败模式 | 本方案的对策 |
|---|---|
| 被完整感骗过（2000 行、章节齐全 → "设计很完整"） | 固定 15 维度 × 20 漏项 × 17 场景卡，逐项给结论 |
| 审成了写作（挑表述、建议加图） | 每条发现必须能写成反例，否则只能进附录 |
| 每次不一样（想到哪问到哪） | 固定镜头/维度 + 固定批次 + 落盘 + 闸门，结论可复现、可追溯 |

## 设计评审怎么跑

```
A0 契约校验 → A0.5 批计划 → A1 决策追溯 → A2 15 维度 → A3 20 漏项
→ A4 17 场景卡 → A4.5 去重 → A5 红-蓝-裁（子代理） → A6 报告 → A7 收口
```

- 扫描层按检查方面分 7 组并行（S1 结构 / S2 状态 / S3 执行 / S4 边界 / S5 安全 / S6 工程 / S7 横切）。
- 对抗层按角色串行：红队 → 蓝队 → 裁判，**上下文硬隔离**，裁判只读双方举证。
- 只有 P0/P1 进对抗；折中结论（"部分成立"）一律非法。

## 实现评审怎么跑

```
B0 体检+基准 → B1 锁范围 → B3 断言 → B4 机械核对 → B5 20 镜头
→ B6 承诺核验 → 去重 → 红-蓝-裁 → B8 报告 → B9 收口
```

五类对照：结构、行为、需求、约束、验收。缺任一类都不算"对照过设计"。

基准分三级，报告第 0 节强制标注：

| 等级 | 条件 | 门禁效力 |
|---|---|---|
| L2 | 设计齐全 + 已冻结 + 有设计评审交接块 | 可作放行依据 |
| L1 | 设计齐全 + 已冻结，无交接块 | 可作门禁，注明基准未审 |
| L0 | 无设计 / 未冻结 / 只改代码 | **不作放行依据** |

L0 仍是完整评审（19 个镜头全跑），只是不做设计对照；但**不得出现"符合设计"字样**（闸门强制）。

## 状态与闸门

每次评审一个目录：

```
<reviewDir>/
├── plan.json            # 批次计划，开跑前写死
├── state.yaml           # 只由 state.mjs 写
├── progress.log         # 心跳与完成记录
├── batches/*.json       # 内容权威（tmp → fsync → rename）
├── 06/07/08.json        # 指控 / 辩护 / 裁断
├── gate-result.md
├── REPORT.md            # 11 节，含全部证据
└── SUMMARY.md           # ≤2 页，含"最该关心的三件事"
```

- 权威顺序：**批产物 > 日志 > state**；崩溃后 `recover` 自动对账并丢弃"有日志无产物"的批。
- `gate.mjs` 在出报告前校验覆盖度、对抗完整性、基准标注、可追溯性；不通过只能出 `DRAFT`。

## 评价指标（怎么知道它有效）

| 指标 | 目标 |
|---|---|
| 漏检率（用历史人工审计当 ground truth） | 代码侧命中 ≥70%，P0 命中 ≥90% |
| 噪声率（真问题占比） | 首版 ≥60%，成熟后 ≥80% |
| 复现性（同输入 3 次，Jaccard） | ≥0.7 |

## 已跑通的端到端验收

在一个真实的 closed 设计集上（13 份文档 / 5.8k 行 / reopen 23 次）跑标准档：

- 覆盖：15/15 维度、100/100 格漏项、17/17 场景卡
- 扫描 7 组 + 红蓝裁 3 角色（子代理执行，11 个实例）
- 去重后 68 条发现；38 条候选全部裁断；gate 通过

产物（plan/state/batches/REPORT/SUMMARY）留在本地 `evals/`，不入库——避免把被审项目的内部设计带进公开仓。

## 边界

- 不替代人工判断：最终定性仍需人签字。
- 不保证抓全缺陷；保证的是**漏了什么你能看见**（覆盖矩阵、N/A 理由、"本次没看什么"）。
- 需求本身是否合理、业务价值、合规认证结论，不在能力范围内。
