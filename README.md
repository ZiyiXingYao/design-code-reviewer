# design-code-reviewer

**当前版本：0.4.1**

> 让"评审"从一次性对话变成可复现、可审计的流程：固定判据、批级落盘、红蓝裁对抗、出报告前强制闸门。

两个 CodeBuddy 技能，用来评审「先出设计文档、再出实现」的项目：

| 技能 | 标识符 | 审什么 | 不做什么 |
|---|---|---|---|
| 设计评审 | `design-review` | 设计方案是否合理、功能是否完整、产物是否合规 | 不读代码、不改文档 |
| 实现评审 | `impl-review` | 代码是否兑现了设计 + 通用正确性/安全 | 不评架构合理性、不改代码 |

两者**完全独立、互不调用**。唯一交接物是设计评审报告末尾的「交接块」（设计基线、欠账白名单、设计约束 `C-n`）。

## 安装

```bash
node install.mjs --dry-run     # 看会装到哪
node install.mjs               # 安装到 ~/.codebuddy/skills/{design-review,impl-review}
node install.mjs --uninstall   # 卸载
```

零依赖，需要 Node ≥ 20。

## 斜杠命令

| 命令 | 作用 |
|---|---|
| `/review-resume` | 恢复中断的评审：扫描 `.design-code-reviewer/*-{design,impl}/`，唯一未完成直接续跑，多个则要求选择 |
| `/design-review` | 直接开一轮设计评审（技能自身可被斜杠调用） |
| `/impl-review` | 直接开一轮实现评审 |

`/review-resume` 只负责"接着跑"：沿用原 `plan.json` 与档位，只补 `next_batches` / `pending_steps`，不会重跑已完成批。

## 触发

- 设计评审：「评审设计方案」「这个架构合理吗」「模块划分有没有问题」「这份设计能不能开工」
- 实现评审：「评审代码」「实现符合设计吗」「合并前检查」「这个 MR 有没有问题」

## 它解决什么

评审最常见的三种失败：

| 失败模式 | 本方案的对策 |
|---|---|
| 被完整感骗过（2000 行、章节齐全 → "设计很完整"） | 固定 15 维度 × 20 漏项 × 17 场景卡，逐项给结论 |
| 审成了写作（挑表述、建议加图） | 每条发现必须能写成反例，否则只能进附录 |
| 每次不一样（想到哪问到哪） | 固定镜头/维度 + 固定批次 + 落盘 + 闸门，结论可复现、可追溯 |

## 设计评审怎么跑

```
A0 契约校验 → A0.5 批计划 → A1 决策追溯 → A2 15 维度 → A3 20 漏项
→ A4 17 场景卡 → A4.5 去重 → A5 红-蓝-裁（子代理） → A6 报告 → A7 收口
```

- 扫描层按检查方面分 7 组并行（S1 结构 / S2 状态 / S3 执行 / S4 边界 / S5 安全 / S6 工程 / S7 横切）。
- 对抗层按角色串行：红队 → 蓝队 → 裁判，**上下文硬隔离**，裁判只读双方举证。
- 只有 P0/P1 进对抗；折中结论（"部分成立"）一律非法。

## 实现评审怎么跑

```
B0 体检+基准 → B1 锁范围 → B3 断言 → B4 机械核对 → B5 20 镜头
→ B6 承诺核验 → 去重 → 红-蓝-裁 → B8 报告 → B9 收口
```

五类对照：结构、行为、需求、约束、验收。缺任一类都不算"对照过设计"。

基准分三级，报告第 0 节强制标注：

| 等级 | 条件 | 门禁效力 |
|---|---|---|
| L2 | 设计齐全 + 已冻结 + 有设计评审交接块 | 可作放行依据 |
| L1 | 设计齐全 + 已冻结，无交接块 | 可作门禁，注明基准未审 |
| L0 | 无设计 / 未冻结 / 只改代码 | **不作放行依据** |

L0 仍是完整评审（19 个镜头全跑），只是不做设计对照；但**不得出现"符合设计"字样**（闸门强制）。

## 对抗审查设计（两个技能共用）

所有 P0/P1 必须过 **红队 → 蓝队 → 裁判** 三小轮，由独立子代理执行。目的不是"再看一遍"，而是让结论经过目标相反的对手和第三方裁断。

### 为什么不是"复核"

| 条件 | 缺失后的退化 |
|---|---|
| 角色目标相反（红队要证明错，蓝队要证明对） | 变成"一起找问题"，强度迅速衰减 |
| 上下文物理隔离（独立子代理，不是分轮模拟） | 红队看到辩护就会妥协，辩论变成共识 |
| 强制裁断（只有成立/不成立/未决） | 双方各说各话，最后取"综合意见"= 和稀泥 |

### 三个角色

| 角色 | 目标 | 交付 | 禁止 |
|---|---|---|---|
| **红队** | 证明设计/代码是错的 | 指控：位置 + 机制 + 后果 | 禁"整体良好"；禁无位置判断；禁只挑软柿子（高风险面必须逐项有结论） |
| **蓝队** | 为每条指控找反驳证据 | 辩护：位置 + 反驳机制 | 禁不引位置的辩护；禁"设计如此" |
| **裁判** | 只看证据定成立与否 | 裁断：成立 / 不成立 / 未决 + 理由 | 禁折中；禁以篇幅论胜负；禁读原始文档找新证据 |

可选 **元审**：只检查"程序合规但内容敷衍"（红队是否跳项、裁判是否折中、指标是否越界），不参与定级。

### 隔离怎么做

1. **路径白名单**：红队只读设计/代码 + 弹药库；蓝队只读结构化指控 + 设计/代码；裁判只读 06/07 两份 JSON。
2. **内容裁剪**：给蓝队的是指控字段（位置/机制/后果），剥掉红队推理与语气。
3. **编号打散**：给裁判的指控编号不按红队原始顺序，避免推断思考路径。
4. **硬约束**：裁判禁读原始文档/代码；红队禁读 `07-defense.json`；蓝队禁读 `06` 的推理过程。

### 举证与裁断

| 一方 | 必须提供 | 不提供的后果 |
|---|---|---|
| 红队 | 位置（file:line 或章节）+ 机制（触发条件/反例）+ 后果 | 驳回，计入红队噪声 |
| 蓝队 | 位置 + 反驳机制 | **无效辩护 = 默认承认** |

裁断只有三态：

| 指控 | 辩护 | 裁定 |
|---|---|---|
| 有证据 | 无证据 / 无效 | **成立** |
| 有证据 | 有证据且指向同一机制 | 能给出可执行路径的一方胜 |
| 有证据 | 有证据但指向不同机制 | **未决**（待人工裁定） |
| 无证据 | — | **驳回** |

禁止"部分成立""有一定道理"；双方势均力敌记未决，不记不成立。

### 分层与成本

- **扫描层**：按检查方面分 7 组并行——S1 结构 / S2 状态 / S3 执行 / S4 边界 / S5 安全 / S6 工程 / S7 横切；S7 只读前六组发现，专找组合缺陷。
- **对抗层**：只对 P0/P1 候选；红→蓝→裁串行，保证定级一致。
- **批量上限**：单批发现 ≤15、单批格数 ≤25、子代理 ≤14；超限由 gate G17 拒绝。
- **升级**：蓝队辩护成立时红队可发起一次升级攻击，最多 2 轮，第 3 轮强制裁断；升级率单独记录。
- **重试**：子代理格式不合格最多重跑 2 次；仍不合格记 `failed`，gate 拦截，不出报告——**主 agent 不许顶上**。

### 质量指标（防走过场）

| 指标 | 定义 | 健康区间 |
|---|---|---|
| 红队成立率 | 成立数 / 指控总数 | 30%–60% |
| 蓝队有效辩护率 | 有效辩护数 / 实际辩护条数 | ≥50% |
| 升级率 | 升级轮指控数 / 首轮指控数 | ≤30% |
| 未决率 | 未决数 / 指控总数 | ≤10% |

口径要点：成立率与有效辩护率分母不同，state 必须分别记录 `defended` 与 `valid_defense`；指标由 `08-verdict.json.stats` 重算，不让子代理自报。

### 落盘与闸门

```
<reviewDir>/
├── 06-accusations.json   # 红队返回（权威）
├── 07-defense.json       # 蓝队返回
├── 08-verdict.json       # 裁判返回（含 stats）
└── 08-verdict.md         # approve 时渲染的可读裁断表
```

gate 相关检查：G5 所有 P0/P1 有裁断且无折中；G11 红/蓝/裁齐全且无 failed；G12 四指标由 stats 重算并披露；G17 批量与子代理上限。

### 任务书

红/蓝/裁/扫描/元审的完整任务书在 `skills/design-review/adversarial/` 与 `skills/impl-review/adversarial/`（orchestrator / scout / red / blue / judge / meta）。子代理看不到主会话，任务书必须自包含：角色、KPI、路径白名单、弹药库、输出 schema、覆盖声明。

> 宿主不具备子代理分派能力时，技能直接拒绝运行，不退回单 agent 模拟。

## 状态与闸门

每次评审一个工作目录 + 一个交付目录：

```
<project>/.design-code-reviewer/<YYYY-MM-DD>-<design|impl>/   # 工作目录
├── state.yaml           # 唯一权威，只由 state.mjs / resume.mjs 写
├── plan.json            # 批次计划，开跑前写死
├── progress.log         # 心跳与完成记录
├── batches/*.json       # 内容权威（tmp → fsync → rename）
├── 00-*.md … 05-*.md    # 聚合中间件
├── 06/07/08.json        # 指控 / 辩护 / 裁断
└── gate-result.md

<project>/specs/audit/<YYYY-MM-DD>-<design|impl>/             # 交付目录
├── REPORT.md            # 11 节，含全部证据（进入 reported 即就位）
├── SUMMARY.md           # ≤2 页，含"最该关心的三件事"（进入 reported 即就位）
└── task.md              # 人工批准后生成的修复任务清单
```

- 权威顺序：**批产物 > 日志 > state**；崩溃后 `resume` 自动对账并丢弃"有日志无产物"的批。
- `gate.mjs` 在出报告前校验覆盖度、对抗完整性、基准标注、可追溯性；不通过只能出 `DRAFT`，也不许 `promote`。
- **报告自包含**（G20）：P0/P1 每条按「在哪（完整文件名:行号+章节）/ 什么问题 / 会怎样 / 怎么改」四段写（impl 的位置必须是代码 `file:line`，另给设计对照）；P2/P3 给「位置 / 问题 / 怎么改」三列表。`05-findings.json` 是给 gate、账本与 task.md 用的证据库，**不能**用来代替报告正文。
- `task.md` 每条含 问题 / 影响 / 怎么改（原文不截断）/ 参考文件（`specs/design/` 完整路径）/ 证据位置；分号后的多步改法不会被截掉。
- 报告产出后停在 `reported`，**同时把 REPORT/SUMMARY 交付到 `specs/audit/<id>/`**，人工评审的对象就是这两个成品；报告被修订后用 `state.mjs deliver <reviewDir>` 重新交付。
- `state.mjs approve <reviewDir> --reviewer "<姓名>"` 才生成 `task.md`、按工作副本复核三份成品并置 `closed`。此后工作目录只读。
- 中断恢复：`node <skill>/scripts/resume.mjs <project> --list`；无参数时唯一未完成直接恢复、多个要求 `--id` 选择。

## 已跑通的端到端验收

在一个真实的 closed 设计集上（13 份文档 / 5.8k 行 / reopen 23 次）跑标准档：

- 覆盖：15/15 维度、100/100 格漏项、17/17 场景卡
- 扫描 7 组 + 红蓝裁 3 角色（子代理执行，11 个实例）
- 去重后 68 条发现；38 条候选全部裁断；gate 通过

产物（plan/state/batches/REPORT/SUMMARY）留在本地 `evals/`，不入库——避免把被审项目的内部设计带进公开仓。

## 结构性局限与不适用场景

**测得出**：设计内部自洽、契约完整、代码与设计偏差、特定输入/时序下的缺陷、并发形态违规。

**测不出**：业务价值、需求本身是否合理、极端规模下的真实性能、合规认证结论、团队可维护性。

**不适用**：单文件脚本/一次性原型、需求未想清、分钟级 hotfix、需要签发合规结论的场合、代码量极小但设计极复杂（只跑设计评审）。

**结构性局限**：子代理只是上下文隔离，不是认知独立；红队可能挑软柿子；裁判可能被论证说服；成本与时长未校准；批次粒度可能被规避。

## 边界

- 不替代人工判断：最终定性仍需人签字。
- 不保证抓全缺陷；保证的是**漏了什么你能看见**（覆盖矩阵、N/A 理由、"本次没看什么"）。
- 需求本身是否合理、业务价值、合规认证结论，不在能力范围内。
